## Decisions
- D-1 Five seeded cases: flagship `dit03` (M5 findings, image-only mark, no UDIN), clean control `dce05`, `dit11` (stamp number reused from a prior filing), `dce07` (UDIN structure problem), `dce09` (issuer certificate expired at signing). Built with the existing generators by extending `DEMO_CASES` in `satya_forensics/synth/corpus.py`; no new generator. Why: the prompt asked for a, b, c, d, e; the flagship covers b and c, so five cases cover all. `make synth-check` stays the freshness gate.
- D-2 State lives in the existing hash-chained ledger. Migration `0002` adds `case_id`, `actor` and `detail_json` (canonical JSON text) to `ledger`; `payload_sha256 = sha256(detail_json)`; the chain formula is unchanged. Event types: `document.uploaded`, `source.response`, `check.run`, `manual_task.created`, `disposition.recorded`. Why: one source of truth, nothing to keep in sync, audit view is a read of the ledger. Uploaded PDFs are stored by SHA-256 under `SATYA_UPLOAD_DIR` (own volume) and re-applied from the ledger at API start.
- D-3 Risk band rule (deterministic, no score): HIGH = any flag of severity `critical` or any document `mismatch_detected`; MEDIUM = else any `warning` flag or any document `manual_review_required` or `expired`; LOW = else. Computed from the stored flags whether or not an official has disposed of them (it orders review; it is not a finding; never shown to institutions). The stage-1 private pre-check is not an input. Code: `services/api/src/satya_api/triage.py`; test: `test_band_rule_is_severity_driven`.
- D-4 Queue status (filterable): `awaiting_review` (no flag has a decision), `in_review` (some), `reviewed` (all), `no_findings`. Sort by band (default), institution, findings, status; filter by band and status; all through URL parameters so no client script is needed.
- D-5 Source hub = three adapters on synthetic data, all labelled: CCA offline chain (M6's chain check against the TEST TRUST ANCHOR, shown as an offline channel, not as CCA), `shcil-estamp-mock` (certificate number looked up in the synthetic register of prior filings plus current cases; bound to another filing gives `manual_review_required`, number absent gives `source_unavailable`), `icai-udin-mock` (a UDIN whose structure, year, membership and uniqueness checks passed is accepted; this is a structure mock, not an ICAI lookup). Every response name carries `MOCK SOURCE`. Final label = most severe check outcome (existing `document_label`), so a valid uploader DSC still never makes a document verified.
- D-6 `source_unavailable` documents get a `manual_task.created` ledger entry and appear in the case view and alerts (the RB-09 screen itself is not built).
- D-7 Alerts are derived at read time from stored data (High band, `valid_to` dates on checks, `expired` labels, manual tasks). "Today" for expiry is the latest document upload date of the case, so the demo gives the same result on any day. Alert type/subtype names follow Portal §2.9 where one exists; `new_high_band`, `certificate_expired`, `expiring_soon` and `source_unavailable_task` are demo subtypes [ASSUMED].
- D-8 Dispositions use the exact names from UI spec §4.2 and `disposition.schema.json`; reason >= 10 characters enforced in the browser, the server action and the API; every record carries `advisory: true`, `regulatory_effect: "none"`. A later decision on the same flag is a new ledger entry; the latest one is shown.
- D-9 "Why" sentences are fixed templates per rule id (`WHY` in `triage.py`) filled only with the flag's own extracted and expected values. No model.
- D-10 Evidence viewer: PDF.js (`pdfjs-dist` 5.7.284, Apache-2.0, self-hosted worker) in a client component; regions are the normalised boxes already on each flag (origin top left, checked on a rendered page). The PDF reaches the browser through the workbench's own `/pdf/<case>/<doc>` route, which calls the gateway with the official's token. CSP gained `worker-src 'self' blob:`.
- D-11 Uploads: raw `application/pdf` body to the API (`POST /v1/cases/{id}/documents?slot=&filename=`), name must match `*.pdf`, content must start `%PDF-` and end with `%%EOF`, 5 MB, unreadable PDFs are rolled back (not stored, nothing in the ledger), per-user upload limit 20/minute, 413 above the limit on that route only. The workbench server action accepts 6 MB. `uploaded_at` of the replaced document is kept so the signing-order check is not confused by the real clock; the real time is in the ledger entry.
- D-12 Audit view: RB and AU roles. AU sees every entry; RB sees entries of cases in their region. The chain is recomputed on every request (prev link, hash, and detail text hash); a tampered row is reported by number. Opening an entry shows its detail text inline (`<details>`).
- D-13 Hindi: the demo namespace is English text in hi.json, listed as [VERIFY] in `hi.review.json`; Hindi for this slice is out of scope.
- D-14 Git identity kept as configured in this environment (owner instruction, overrides the prompt's rule). Branch `demo-slice`, not the session branch (owner instruction).
- D-15 Reset: `make demo-reset` regenerates and checks the synthetic files, rebuilds the api image, empties `ledger` and `inbound_events` as the Postgres superuser with the user triggers disabled (demo database only), clears the uploads volume, restarts the api and runs `satya_api.demo_seed`. Case data is identical on every reset; ledger timestamps and hashes differ.
- D-16 Not run in the cloud session: the Docker stack (no daemon). Verified instead: API unit tests (MemoryStore), migration 0002 and the seed on a local Postgres 16, the built web app driven by Chromium against the real API with a test token verifier (queue, filters, case, viewer, decision, pick, bad upload, audit, alerts, 375 px, no console errors). `make demo-reset` and `make e2e` need the team's laptop.
- D-17 Real 404 for unknown and malformed case IDs: `case/[id]/loading.tsx` (added in D4) wrapped the nested `affidavit/layout.tsx` and `verification/layout.tsx` in a Suspense boundary, so their `notFound()` ran after the shell had streamed and the status stayed 200 (the "layout awaits before loading.tsx streams" assumption in `src/lib/cases.ts` no longer held). Fix is in the app, not the test: the case view page, its `loading.tsx` and `upload/` moved into the route group `case/[id]/(review)/` (URLs unchanged), so the loading boundary no longer covers the affidavit and verification layouts. The assertions in `tests/e2e/diffview.cjs` are unchanged. A non-RB user still gets 403 from `case/[id]/layout.tsx`, which sits above every boundary.
