# Decisions: blind evaluation set and deterministic replay (branch `blind-eval-replay`)

- BR-1: A rule pack id is `m5-affidavit@<version>+m6-signatures@<version>` and is what `rule_version` means in the replay endpoint and CLI. The current pack comes from `packages/rules`; archived packs are folders `<archive>/<pack id>/` holding both files (default `packages/rules/archive`, override `SATYA_RULES_ARCHIVE_DIR`). The allow-list is the current id plus folder names that match the id pattern, so a client never chooses a path.
- BR-2: Flags are not stored as rows today (they are recomputed), so B1 adds the replay record to the `check.run` ledger entry's detail JSON: `rule_pack`, `checked_at`, `doc_hashes`, `flags` (id, doc, rule id, rule version, check ref, severity, label, page, evidence hash), `source_responses`, and `engines.ruleset_m5`. The detail is JSON inside the existing `detail_json` column, so no database migration is needed (additive by construction). Entries written earlier lack `rule_pack`; they read as `unknown` and are reported `ORIGINAL_UNKNOWN`, with no replay.
- BR-3: The endpoint is `GET /v1/cases/{case_id}/replay` (the gateway's prefix; through the proxy it is `/api/v1/cases/{case_id}/replay`).
- BR-4: Roles `RB` and `AU` may replay (the two roles that already read the ledger); `RB` is limited to the case's region, `AU` sees all, as for `/v1/audit`. Own limiter `SATYA_REPLAY_RATE_LIMIT` (default 10/minute per user). Lists in the response are capped at 500 items (`truncated: true`).
- BR-5: Replay at a different rule pack reports `reproducible: true` when every input verified (chain, vault hashes, stored source answers) and the run completed; `identical_to_original` says whether the result matches. At the original pack, `reproducible` means identical.
- BR-6: Source answers come from the ledger (`source_responses` of the original `check.run`) through `apply_stored`; no adapter is called. The local register of stamp numbers and UDINs (used by the reuse rules inside M6) is read as it is now; if it changed since, the result differs and the reason is `RESULT_DIFFERS`. Limit stated, not hidden.
- BR-7: The ledger chain is verified as a whole before every replay. One broken link anywhere returns `HASH_MISMATCH` with `ref: ledger:<seq>`; a vault document whose bytes no longer match the hash recorded at the original run returns `HASH_MISMATCH` with the document id. Both are logged as security events.
- BR-8: A `case.replay` entry appears in the audit list; the workbench has no message key `audit.event.case_replay` yet (apps/web is out of scope here). Listed in DEFERRED.md.
- BR-9: Guard against tuning rules on the blind set: a pytest (`packages/blindgen/tests`, `test_blind_results_and_rule_files_do_not_change_in_the_same_commit`) fails when the last commit changes a `packages/rules/*.yaml` file and `docs/eval/blind-results.json` or `BLIND-REPORT.md` together. It skips when git history is unavailable (shallow CI checkout). Chosen over a CONTRIBUTING note because the repo has no CONTRIBUTING file; the rule is also stated in the blindgen README.
- BR-10: The generator reads only the affidavit template file (the input a portal hands any tool), the rule files for the label each rule gives (spec data, used for the expected document label) and the project's PDF signing helper and test PKI (low-level primitives). It imports no case definitions or expected tables; a test enforces the import rule. Declaration text substitution, layout, dates, ids, tables, stamp page, accounts and every anomaly are its own code.
- BR-11: A rule counts as fired on a document if any flag of that rule is present for it (presence per document), not per flag; M5 flags are attributed to the affidavit document because M5 names documents by content hash.
- BR-12: Generator defects found while developing it against the engine (unruled tables read as no table; unstruck "/" separators between option choices; room ids repeated across blocks) were fixed in the generator before sealing. No rule or engine code was changed. After sealing, the generator is frozen for the reported run.
- BR-13: Not planted by this generator (listed in DEFERRED.md and in the report): land and room reconciliation anomalies, stamp reuse, UDIN reuse, revoked and expired certificates, source-hub states, scan fallback reason codes.
- BR-14: New dependency: reportlab==5.0.1 for the generator (BSD licence; already a dev dependency of the workspace).
